# 1. Описание проекта

В качестве исходного приложения выбран **[Bob’s Used Books](https://github.com/aws-samples/bobs-used-bookstore-sample)** — учебный проект интернет-магазина Б/У книг, разработанный как монолитное веб-приложение на платформе .NET.

Приложение построено на **ASP.NET Core MVC** и использует **Microsoft SQL Server** для хранения данных. Пользовательская часть позволяет просматривать и искать книги, добавлять их в корзину, оформлять заказы, работать со списком желаемого и предлагать собственные книги магазину для продажи.

В приложении также предусмотрена административная часть для управления ассортиментом, остатками книг, заказами и предложениями пользователей.

На текущем этапе система представляет собой **монолитное n-tier приложение**: основные бизнес-функции работают в рамках одного приложения и используют общую базу данных. Поэтому проект подходит для анализа и последующей разработки плана декомпозиции на микросервисы.

# 2. Анализ монолита

Bob’s Used Books состоит из нескольких логических слоёв, но все основные функции работают как единое приложение и используют общую базу данных.

Основные части проекта:

- `Bookstore.Web` — MVC-контроллеры, страницы и пользовательский интерфейс;
- `Bookstore.Domain` — бизнес-логика приложения;
- `Bookstore.Data` — работа с данными через Entity Framework Core;
- `Bookstore.Cdk` — описание инфраструктуры AWS;
- `Bookstore.Domain.Tests` — тесты бизнес-логики.

Основные бизнес-области приложения:

- книги и складские остатки;
- корзина и список желаемого;
- заказы;
- покупатели и адреса;
- предложения пользователей о продаже книг

Все эти области связаны через общие модели и одну базу данных. Например, при оформлении заказа приложение одновременно работает с корзиной, книгами, покупателем и заказом.

Упрощённо текущая архитектура выглядит так:

```text
Bookstore.Web
      ↓
Bookstore.Domain
      ↓
Bookstore.Data
      ↓
   SQL Server
```

# 3. Выделение микросервисов и границы ответственности

На основе анализа монолита были выделены основные бизнес-области, каждая из которых может быть вынесена в отдельный микросервис.

| Микросервис        | Ответственность                                             | Основные сущности                  |
| ------------------ | ----------------------------------------------------------- | ---------------------------------- |
| `Book Service`     | управление книгами, ценами, остатками и справочными данными | `Book`, `ReferenceDataItem`        |
| `Cart Service`     | корзина пользователя и список желаемого                     | `ShoppingCart`, `ShoppingCartItem` |
| `Order Service`    | создание и обработка заказов                                | `Order`, `OrderItem`               |
| `Customer Service` | данные покупателей и адреса доставки                        | `Customer`, `Address`              |
| `Resale Service`   | предложения пользователей о продаже книг магазину           | `Offer`                            |

После декомпозиции каждый сервис должен управлять только своими данными. Прямой доступ к данным другого сервиса исключается — взаимодействие выполняется через API.

Например, `Order Service` не должен напрямую обращаться к таблице книг, а должен получать необходимые данные через `Book Service`.

# 4. Взаимодействие микросервисов

После декомпозиции сервисы не обращаются напрямую к чужим таблицам. Необходимые данные они получают через API.

Для внешних запросов используется **REST**, а для внутреннего взаимодействия между микросервисами — **gRPC**.

| Взаимодействие                        | Назначение                                      | Протокол |
| ------------------------------------- | ----------------------------------------------- | -------- |
| Клиент → `API Gateway`                | единая точка входа в приложение                 | REST     |
| `API Gateway` → `Book Service`        | просмотр и поиск книг                           | REST     |
| `API Gateway` → `Cart Service`        | работа с корзиной и списком желаемого           | REST     |
| `API Gateway` → `Order Service`       | оформление и просмотр заказов                   | REST     |
| `API Gateway` → `Customer Service`    | работа с данными покупателя и адресами          | REST     |
| `API Gateway` → `Resale Service`      | создание и просмотр предложений о продаже книг  | REST     |
| `Cart Service` → `Book Service`       | получение актуальных данных о книгах в корзине  | gRPC     |
| `Order Service` → `Cart Service`      | получение содержимого корзины                   | gRPC     |
| `Order Service` → `Book Service`      | проверка цены и наличия книг, изменение остатка | gRPC     |
| `Order Service` → `Customer Service`  | получение данных покупателя и адреса доставки   | gRPC     |
| `Resale Service` → `Customer Service` | получение данных пользователя                   | gRPC     |
| `Resale Service` → `Book Service`     | получение справочных данных о книге             | gRPC     |

Например, при оформлении заказа взаимодействие выглядит следующим образом:

```text
Клиент
  │ REST
  ▼
Order Service
  ├── gRPC ──► Cart Service
  ├── gRPC ──► Customer Service
  └── gRPC ──► Book Service
```

# 5. План миграции

Декомпозиция будет выполняться постепенно с использованием **Strangler Pattern**: отдельные функции поэтапно выносятся из монолита в микросервисы, при этом оставшаяся часть приложения продолжает работать.

Предлагаемый порядок миграции:

1. **Book Service** — вынести работу с книгами и справочными данными.
2. **Customer Service** — перенести данные покупателей и адреса.
3. **Cart Service** — вынести корзину и список желаемого.
4. **Resale Service** — перенести работу с предложениями о продаже книг.
5. **Order Service** — вынести последним, так как оформление заказа зависит от корзины, книг и данных покупателя.

При выделении каждого сервиса выполняются следующие действия:

- перенос соответствующей бизнес-логики;
- создание отдельной базы данных;
- замена прямых обращений к данным вызовами REST или gRPC;
- перенаправление запросов из монолита в новый сервис;
- удаление старого модуля после проверки работы сервиса.

В результате функциональность монолита постепенно уменьшается, пока все выделенные бизнес-области не будут перенесены в независимые сервисы.
